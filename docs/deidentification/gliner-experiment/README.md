# GLiNER vs Stanford+Track D: experiment kit

You are testing whether a GLiNER-based PHI redaction approach beats a
rule-based baseline on the MedDeID benchmark. This is a clean head-to-head
evaluation.

## Objective

Determine if GLiNER (with LLM-generated label descriptions) beats the
current best system on the frozen MedDeID test-100 set.

**Baseline to beat (frozen, do not modify):**
- Stanford NER + Track D deterministic rules (D1-D12)
- Exact-span F1: 0.8718
- Character recall: 0.9532

## Why this matters

Track D rules are hand-written regex patterns that overfit MedDeID's
synthetic data (they drop to 0.42 F1 on SHIELD, a different dataset).
GLiNER is a zero-shot NER model that takes natural-language label
descriptions and finds matching spans without training. If an LLM can
auto-generate good descriptions from unlabeled notes, we get a system that
adapts to new data with zero user effort: no fine-tuning, no hand-written
rules, no labeled data.

## Layout

Everything the experiment needs is in this directory, which lives at
`docs/deidentification/gliner-experiment/` in the `prerounding-checklist`
repo. No machine-specific paths.

- `kit/data_loader.py`: `load_test100()` returns
  `(gold_by_id, notes_by_id, trackd_preds_by_id)` for the frozen test-100.
- `kit/scoring.py`: `exact_scores(gold, preds)` and
  `paired_f1_diff(gold, preds_a, preds_b)`. Same scorer and schema as the
  frozen baseline, so numbers are directly comparable.
- `kit/labels.py`: the frozen `LABELS` dict (descriptions below, also
  importable).
- `kit/conflict.py`: the frozen Arm 3 conflict-resolution rule plus the
  Arm 2 overlap-dedup helper.
- `schemas/`: frozen scoring code (`score.py`, `adapter.py`,
  `meddeid-15.json`).
- `data/`: frozen test-100 notes (`notes_test100.jsonl`), gold labels
  (`gold_test100.json`), and the Track D reference predictions
  (`stanford_trackd_test100.json`, the 0.8718 baseline).

## Arms to run

### Arm 1: Stanford + Track D (frozen reference)

Already computed: `data/stanford_trackd_test100.json`. Load it with
`load_test100()`. Do not recompute or modify. This is your 0.8718 baseline.

### Arm 2: GLiNER alone

For each note in test-100:
1. Run GLiNER with the frozen label descriptions above.
2. Use threshold=0.5 (preregistered, do not tune).
3. Map GLiNER's output labels to the MedDeID types (exact match on the
   keys above). Emit spans as `{begin, end, text, type}`.
4. Resolve overlapping spans with `kit/conflict.py::dedup_by_confidence`
   (keep the highest-confidence span).

### Arm 3: GLiNER + Track D

Combine with `kit/conflict.py::combine_trackd_gliner` (preregistered):
1. Start with all Track D predictions (deterministic, high-precision).
2. Add GLiNER predictions that do not overlap any Track D span.
3. For overlapping spans: keep Track D's span (deterministic wins ties).

## Test set

The frozen test-100 split is `data/gold_test100.json` /
`data/notes_test100.jsonl` (100 notes). Use exactly this split.

**CRITICAL: Do not inspect test-100 notes or labels before running. Do not
tune thresholds, modify descriptions, or adjust the conflict-resolution
rule based on test-100 errors. All parameters are frozen above.**

## Report format

For each arm, report:
1. Exact-span precision, recall, F1 (with 95% CI).
2. Character recall (with 95% CI).
3. Per-concept F1 (which PHI types does GLiNER help/hurt?).
4. Paired difference vs the 0.8718 baseline (bootstrap CI on the F1
   difference, via `paired_f1_diff`).
5. Model size on disk and download size.
6. Average CPU latency per note (seconds).
7. Whether the model could plausibly run in a browser via ONNX/WebGPU.

## Success criterion

GLiNER + Track D (Arm 3) beats 0.8718 F1 with a bootstrap 95% CI that
excludes zero difference. If it does, the LLM-generated description
approach is validated. If not, the Track D rules remain the best system.

## What was already tried

- GLiNER 0.2.29 installs and imports correctly.
- HuggingFace model downloads were blocked in the cloud VM (proxy issue);
  retry on a machine with normal HuggingFace access.
- LLM-as-extractor (Qwen 30B doing NER directly) scored 0.29 F1 on a
  20-note pilot, far below 0.87. This does NOT test GLiNER; it tests a
  general LLM prompted to do NER, which is a different architecture.
- The descriptions above were validated as useful (they guided the LLM to
  find correct entities), but the LLM extraction step is not competitive.
