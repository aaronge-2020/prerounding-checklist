# Workstream 1 — Review-gate validation: report

## What this is, and what it is not

This workstream measures the app's **clinician review gate**: the modal where
a human sees the pipeline's de-identification suggestions, accepts or rejects
each one, and manually redacts anything the automation missed.

**Read this first:**

- The two reviewer conditions below are **simulated bounds, not human data**.
  The "accept-all" reviewer is a hypothetical rushed rubber-stamper; the
  "oracle" reviewer is a theoretical perfect reviewer that never misses and
  never misjudges. Neither represents real clinician behavior. They bracket
  the range real performance should fall inside.
- The oracle's perfect score (1.0/1.0/1.0) is **by construction** — it is not
  a claim about achievable performance. The empirical finding is *what the
  oracle had to add by hand*, per PHI category: that is the work a real human
  must do to reach safety.
- Real reviewer sessions have not been run yet. The ready-to-run protocol for
  them is in `reviewer_protocol.md`, with a blank results template in
  `reviewer_results_template.csv`.
- All 60 notes are **synthetic** (invented names, dates, numbers). No real
  PHI, no IRB implications.

## Method

**Notes.** 60 synthetic clinical notes generated by `gen/gen_notes.py`
(seed 20260929): 20 discharge summaries, 20 nursing notes, 20 progress
notes; 157–201 words each; 6–10 PHI items per note (480 total) across
PATIENT names, PROVIDER names, DATEs, PHONEs, ADDRESSEs, MRNs (ID), AGEs,
and HOSPITALs (FACILITY). Ground truth is character-offset annotations
recorded at generation time (`notes.jsonl`: id, note_type, text,
entities[{start,end,label}]). The generator enforces two invariants: every
note is within the word/PHI budget, and **every occurrence of every PHI
string is covered by an entity span** (a leak check that fails the build if
any PHI is smuggled into the text without annotation).

**Pipeline run.** The real de-identification pipeline (the app's shipped
`deid.bundle.js`: `onnx-community/stanford-deidentifier-base-ONNX`
quantized NER + deterministic rules + temporal handling + alias expansion,
hybrid mode) was run over all 60 notes in headless Chromium via the
benchmark's driver pattern (`harness/driver.mjs` + `harness/server.mjs` +
`harness/site/`). Per note the driver captured the full suggestion list
(spans, labels, placeholder renderings), the redacted text, and residual
warnings → `pipeline_suggestions.json`. No data left the machine.

**Scoring** (`score_ws1.py` → `results.json`). Primary metric: exact-span
(start + end + category) match. Secondary: span-only exact, entity overlap,
character-level. Predicted labels were folded to the eight gold categories
(PATIENT NAME/CONTACT NAME→PATIENT, PROVIDER NAME→PROVIDER, DOB→DATE,
MRN/ENCOUNTER ID→ID, FACILITY/LOCATION/ORGANIZATION→FACILITY).

**Reviewer simulation.** (a) *Accept-all*: every suggestion accepted, nothing
added — post-review metrics equal the automated metrics; residual PHI is
whatever the automation missed. (b) *Oracle*: every suggestion overlapping
real PHI accepted, all others rejected, every uncovered gold character
manually redacted. Post-review precision/recall/F1 are 1.0 by construction;
the reported finding is the count and category of manual additions.

**Review-state validation** (`analysis/validate_review_state.mjs`). The
app's real review-state constructor
(`src/patient-context/review.js :: createEphemeralRedactionReview` — the
exact function whose output the review modal renders) was driven in Node
over 10 notes spanning all three note types, fed with real pipeline output.
Checked: (1) the pending-suggestion list equals the pipeline entity list
(modulo the constructor's documented dedup of identical/overlapping spans);
(2) accept-all at review-state level reproduces the pipeline's redacted
text; (3) oracle decisions at review-state level match entity-level counts.

## Results

### Condition (a): accept-all reviewer (lower bound)

| Metric | Precision | Recall | F1 |
|---|---|---|---|
| Exact-span | 0.869 | 0.867 | 0.868 |
| Span-only exact | 0.869 | 0.867 | 0.868 |
| Entity overlap | 0.877 | 0.875 | 0.876 |
| Character-level | 0.911 | 0.933 | 0.922 |

(tp=416, fp=63, fn=64 over 480 gold spans.)

Per-category exact-span:

| Category | Gold | P | R | F1 | Missed |
|---|---|---|---|---|---|
| PATIENT | 80 | 1.000 | 0.825 | 0.904 | 14 (all partial/boundary) |
| PROVIDER | 120 | 0.873 | 0.975 | 0.921 | 3 |
| DATE | 100 | 0.629 | 1.000 | 0.772 | 0 |
| PHONE | 20 | 1.000 | 1.000 | 1.000 | 0 |
| ADDRESS | 20 | 1.000 | 1.000 | 1.000 | 0 |
| ID (MRN) | 20 | 1.000 | 1.000 | 1.000 | 0 |
| AGE | 60 | 0.000 | 0.000 | 0.000 | **60 (all)** |
| FACILITY | 60 | 1.000 | 1.000 | 1.000 | 0 |

Per note type (exact-span recall / precision):
discharge 0.900/0.900, nursing 0.850/0.938, progress 0.833/0.746.

**Residual PHI under accept-all: 60 age spans — every one of the 60 notes
leaks its age mention.** No other category has a fully-missed span; the 14
missed patient names all had partial suggestion overlap (boundary or label
variants), and the 3 missed provider spans likewise.

### Condition (b): oracle reviewer (upper bound)

- Suggestions accepted: **420**; rejected: **59**; manual additions: **61 spans**.
- Post-review precision/recall/F1: **1.0 / 1.0 / 1.0 by construction**.
- Manual additions by category ("what the human has to catch"):

| Category | Spans hand-added | Characters |
|---|---|---|
| AGE | 60 | 480 |
| PROVIDER | 1 | 4 (boundary: ", RN" after a caught name) |
| all others | 0 | 0 |

The 59 rejected suggestions: 59 relative-date expressions the pipeline
deliberately surfaces ("within one week", "this morning", …) — counted as
rejects here only because they don't overlap gold spans; a real reviewer
following the app's design would accept most of them (they render as
relative timeline markers). Genuine false alarms were a handful of
boundary variants (e.g. "Notified Dr. X", "with <name>").

### What the bounds mean

- **Lower bound.** A reviewer who rubber-stamps every suggestion still gets
  0.87/0.87 exact-span — but leaks **age in 100% of notes** and leaves
  boundary fragments on names. The automation is strong on
  phones/addresses/MRNs/facilities (all 1.0) and dates (1.0 recall), weak on
  patient-name boundaries, and blind to ages.
- **Upper bound.** A perfect reviewer closes everything, at a cost of
  ~1 rejection and ~1 manual redaction per note — and the manual work is
  almost entirely **ages** (60 of 61 spans). The single biggest thing the
  human gate exists to catch, on this data, is the age mention.
- **The gap between them is the reviewer's real job**: ages first, then
  name-boundary cleanup, then filtering a small number of false alarms.
  Real human sessions (protocol in `reviewer_protocol.md`) will show where
  between these bounds clinicians actually land — expected well above the
  lower bound on ages (ages are easy for humans to spot) and below the
  oracle on boundary fragments.

### Review-state validation (real UI-adjacent code, 10 notes)

- The real `createEphemeralRedactionReview` produced **84 suggestions from
  84 pipeline entities** — a 1:1 mapping on this subset (the constructor's
  dedup of identical/overlapping spans did not trigger; it remains the one
  documented way the modal's list can be shorter than the raw entity list).
- Oracle decisions at review-state level **matched entity-level simulation
  exactly** (accepted 72/72, rejected 12/12, manual additions 10/10).
- A naive "splice placeholders into source" reproduction of the final
  accept-all text differs from the pipeline's redacted text on 7/10 notes —
  this is expected, not a defect: the pipeline's *text renderer* applies two
  deliberate transforms the review-state constructor does not own
  (renaming date field labels like "Date:" to "Timeline:" before relative
  timeline placeholders — a design choice so the output reads as a timeline —
  and trailing-whitespace trimming). The review-state constructor owns only
  the suggestion list and redaction records, which match exactly.

**What was NOT driven:** the DOM modal itself (suggestion rows, Accept
all/Reject all buttons, floating Redact pill, acknowledgment checkbox).
The modal is wired into the authenticated chat shell and cannot be isolated
in headless Chromium without re-implementing the app around it. The
protocol in `reviewer_protocol.md` exercises the real modal with human
reviewers.

## Limitations

- Synthetic notes are cleaner and more formulaic than real documentation;
  template repetition (e.g. "within one week" in all 20 discharge summaries)
  inflates some counts. Treat miss rates as a lower bound on real-world
  performance, not an estimate of it.
- The oracle is theoretical. Do not cite its 1.0 as achievable.
- Ages in these notes are 19–97 in prose ("77-year-old", "83 years old").
  The pipeline caught none in any format; whether a production age-detector
  should be added is a product decision this data informs but doesn't make.
- Only the default model (`stanford-deidentifier-base-ONNX`, quantized) was
  tested, in hybrid mode — the configuration the app actually ships.
- Timing (headless shell, this machine): median ~6.0 s/note end-to-end,
  p95 ~9.8 s.
