# Workstream 3 — Deployment Envelope: model size, memory, startup, latency, fail-closed, throttled proxy

Target: the browser-local clinical de-identification pipeline used by the pre-rounding app
(ONNX NER model `onnx-community/stanford-deidentifier-base-ONNX`, quantized q8, ONNX Runtime
wasm via Transformers.js in Chromium + deterministic rules + clinician review gate; all on-device).

All measurements below were taken on THIS machine only (AMD EPYC 9D25, 2 vCPUs, ~8 GB RAM,
headless Chromium via Playwright) and must not be generalized to other devices.

> **Environment caveat (applies to every timing number):** this 2-vCPU VM was shared with
> other concurrently-running benchmark workloads for the whole session (load averages
> roughly 4–9 observed; a sibling workstream's Chromium was actively benchmarking at the
> same time, and the box rebooted mid-session). Timing numbers are therefore *contended*
> and slower than the prior 2026-09-29 baseline (model load ~4.9 s; hybrid median 647 ms /
> p95 1,266 ms on 1,000 ai4privacy texts). Text length does **not** explain the gap: the old
> sample's median length was 434 chars vs 423 chars for the notes used here. The gap is
> attributed to CPU contention. A dedicated-machine re-measurement is still needed for
> publication.

## Methods

- Harness: the existing benchmark harness was reused unmodified
  (`~/workspace/deid-benchmark/harness/driver.mjs` + `server.mjs`, pipeline modules in
  `pipeline-src/`). A sibling workstream's identical harness server was already listening
  on 127.0.0.1:8902 (same site dir, same COOP/COEP/no-store headers, model bytes verified
  identical at 109,651,017), so the stock-harness phases ran against it; this changes
  nothing about what was measured. ws3 additions live in
  `~/workspace/deid-validation/ws3-envelope/`: an overlay probe page
  (`overlay/failclosed.html`, a copy of `harness.html` with a visible status panel and a
  capture API) served by `scripts/server_ws3.mjs` on port 8931 (overlay-first, falls back
  to the benchmark site tree; same headers).
- Synthetic data only: 150 invented clinical-style notes (`data/notes_ws3.jsonl`,
  generated by `scripts/gen_notes.py`; median 423 chars, range 329–601). No real PHI;
  nothing was sent to any remote model API.
- Latency: per-document `performance.now()` around `deidentifyText(..., {mode:"hybrid"})`,
  batches of 10, one warm-up inference inside `load()` (same as the prior baseline).
- Memory: CDP `Performance.getMetrics` (`JSHeapUsedSize`) + `/proc` RSS summed over the
  whole browser process tree, sampled ~5×/s during load. `performance.memory` appeared
  frozen in this headless build (constant 44,700,000 across all samples) and was not used.
  The JS heap barely moves during load (24.5 → 32.1 MiB) while RSS jumps ~600 MiB: the
  model weights live in WASM linear memory, which counts toward process RSS, not the JS heap.
- Startup: cold = fresh browser profile per run (empty cache); warm = reused persistent
  profile after one pre-warm load. The static server sends `Cache-Control: no-store`, so
  "warm" here measures repeat-fetch + init, not HTTP-cache hits — warm ≈ cold within noise
  is expected, and observed (warm median load 14,956 ms vs cold 10,282 ms; ordering
  flipped by contention noise).
- Fail-closed: Playwright request routing against the overlay page. The harness remaps
  `https://huggingface.co/…` requests to same-origin model files (exactly as the app's
  `deid-service.js` does), so aborting `**/models/onnx-community/**` is the faithful
  equivalent of blocking the HF CDN. Corrupted-weights case serves the real
  `model_quantized.onnx` with a 1 MiB window overwritten (same byte count, served
  200 OK) — i.e. a corrupt cache entry that still "downloads" fine.
- Throttling: CDP `Emulation.setCPUThrottlingRate({rate: 4})` applied to the whole page
  (load + 50 docs). **This is a simulated proxy, not a real low-end device test.**

## Fail-closed transcript

### Scenario A — model CDN blocked (requests to the model path aborted)

Pipeline level (`createDeidentifier().loadModel()`, single candidate), captured verbatim:
- `load()` **rejected after 33 ms** with: `"Failed to fetch"`
- Status callback sequence (user-visible progress text):
  1. `"Preparing local PII model. First load can take a minute."` (ready: false)
  2. `"Model unavailable; structured redaction only."` (ready: false)
- Console warning: `"Could not load de-ID model
  onnx-community/stanford-deidentifier-base-ONNX. TypeError: Failed to fetch"`
- A subsequent `deidentifyText()` **did not throw** — it returned `{ok: true, modelId: null}`
  (the pipeline degrades to its structured-rules layers with zero model entities; the
  `modelId: null` is the signal the app layer keys on).

App level (static trace through the shipped code — the review gate guarding every send):
- `deid-service.js → deidentifyText()` catches the load failure, sets model status
  `"model unavailable"`, and **throws**
  `"Stanford clinical unavailable (<detail>). Select Structured only if you want to run
  the fallback redactor."` unless the caller explicitly opts into the structured fallback
  (`allowStructuredFallback`, default false at every call site checked).
- The AI-chat review flow calls it with `allowStructuredFallback: false`
  (`src/ui/ai-chat/controller.js` → `deidentifyForReview`), and additionally refuses any
  result with `!result.modelId || result.modelChunkFailures`, throwing
  `"the de-identification model didn't return a usable result for …"`.
- The review's catch block renders the failed-review modal (`canSend: false`, no Send
  button). Verbatim user-visible text (`src/ui/ai-chat/presentation.js`):
  - Heading: **"De-identification failed — sending is blocked"**
  - Detail: **"De-identification failed (Stanford clinical unavailable (Failed to fetch).
    Select Structured only if you want to run the fallback redactor.) — nothing was sent."**
  - **"Close this dialog and try again. Nothing from this send left the browser."**
- The structured-only fallback exists but is a **separate, explicitly user-selected mode**;
  the send gate blocks structured-only content from the remote-send path
  ("Structured-only mode is blocked by the send gate before this is ever called").

**Verdict: fail-closed holds at the app level — nothing is sent and the user gets an
explicit blocked-send modal.** One honest nuance: the raw pipeline's `deidentifyText()`
does not itself throw on model failure (it degrades to rules-only with `modelId: null`);
fail-closed is enforced by the service + controller layers checking that signal. Any
future caller of the pipeline that ignores `modelId` would silently get rules-only output.

### Scenario B — corrupted cached weights (valid HTTP 200, corrupt ONNX bytes)

- `load()` **rejected after 2,878 ms** with:
  `"Can't create a session. ERROR_CODE: 7, ERROR_MESSAGE: Failed to load model because protobuf parsing failed."`
- Same status sequence as Scenario A
  (`"Preparing local PII model. First load can take a minute."` →
  `"Model unavailable; structured redaction only."`).
- Console warning: `"Could not load de-ID model
  onnx-community/stanford-deidentifier-base-ONNX. Error: Can't create a session.
  ERROR_CODE: 7, ERROR_MESSAGE: Failed to load model because protobuf parsing failed."`
- Subsequent `deidentifyText()` again returned `{ok: true, modelId: null}` — same
  app-level refusal path as Scenario A applies.
- Screenshots: `results/failclosed/blocked.png`, `results/failclosed/corrupted.png`
  (probe page showing the LOAD FAILED panels with the thrown error text).

## Throttling caveat

The 4× CPU-throttle run is a **simulated proxy only**. CPU throttling slows the main
thread but does not reproduce a real low-end device: different CPU microarchitecture and
instruction throughput, different (often much smaller) RAM, thermal-throttling behavior,
slower storage for the ~110 MB model fetch, and mobile power/thermal governors are all
unmodeled. **The real-device test still needs doing.**
